# [Developer documentation](@id developer_overview)

Welcome! These pages are for those who want to change the package, or to understand how it works
inside. You do not need them to use LinearDecisionRules.jl: the rest of the manual covers that.

The package is a reformulation engine. You write a JuMP model, and at `optimize!` the package reads
it, rewrites it as one or more inner optimization problems, solves them with your solver, and
reports the results through JuMP. The pages below follow that path from different angles:

| Page | What you will find |
|---|---|
| [Architecture](@ref developer_architecture) | The big picture: the layers of `src/`, the pipeline from a JuMP model to results, the types that flow through it, and where state lives. Start here. |
| [Call flows](@ref developer_flows) | What runs, step by step, when a model is written, at `optimize!`, at a re-solve, and when results are read. |
| [Public and internal API](@ref developer_api) | Which names are exported, which are documented but internal, and how the JuMP layer talks to the optimizer. |
| [Structure of `src/`](structure_current.md) | A generated reference: each file, what it defines, what it uses and what uses it. |

The mathematics of the formulations (the primal and dual decision rules, the liftings, the moments)
is in the LaTeX notes of
[`docs/math`](https://github.com/bfpc/LinearDecisionRules.jl/tree/main/docs/math).

## Conventions

A few rules keep the code easy to navigate:

- **Layers.** `src/` has one folder per layer. `lifting/`, `canonical/`, `probability/` and
  `formulations/` are the core: they work on a typed description of the problem and know nothing
  of JuMP's modelling layer. `moi/` and `jump/` are the front end that connects the core to JuMP.
  Keeping the core independent means that another front end could replace `moi/` and `jump/`
  without touching the core or its tests.
- **Private names** start with `_`. Exported names are the user API, and a few unexported names
  are documented on the Internals page; see [Public and internal API](@ref developer_api).
- **One concern per file**, named after it.

## How the structure page is made

The page [Structure of `src/`](structure_current.md) is generated by `docs/structure.jl`, which the
documentation build runs. To regenerate it alone, run

```
julia docs/structure.jl
```

The script needs only the standard library. It parses `src/` and records each top-level
definition: its file and line, whether it is exported or documented, and the names it uses. From
this it derives the dependencies between files and between layers, with these rules:

- A file *uses* another when one of its definitions refers to a name whose first definition, in
  include order, is in the other file. A function with methods in several files belongs to the file
  of its first method, and the other files *extend* it. `_build!` and `support_constraints` are
  examples: one file declares the interface, and later files add methods.
- A use inside a function body works even if the defining file is included later, because Julia
  looks names up when the function first runs. The page lists these uses of later files, since
  they read as a layer calling the layer above it.
- A use in a signature, a field type or a constant value is needed when the file is loaded, so a
  use of a later file there would fail to load. The page flags it.
- Local variables that shadow a function name (a variable named `stage`, say) are not uses.
- Methods of functions of other packages (`MOI.get`, `JuMP.build_variable`, `Base.show`) are listed
  under their file, but are not part of the dependency graph, since their callers are in MOI or
  JuMP.

The one-line role of each file comes from `docs/structure_notes.toml`; update it when you add,
split or rename a file.

Two options help to explore the structure. `--explorer structure.html` writes a self-contained
interactive page, with a map of the files by folder, a tree of files and definitions, and the uses
and users of each. `--json structure.json` writes the underlying data. To plan a reorganization,
describe it in a TOML file (moves of definitions between files, renames, new definitions, a new
include order) and pass it with `--proposal proposal.toml`; the script then analyses the proposed
structure in the same way, writes its page with `--proposed structure_proposed.md`, and adds it to
the explorer, with a toggle between the two structures.
